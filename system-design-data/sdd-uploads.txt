Курс «Системный дизайн: данные и надёжность». Урок «Загрузка файлов».

=== раздел ===

Менеджер ресторана обновляет меню из кабинета на телефоне. Он снял тридцать новых блюд и выбирает все фото разом: в среднем каждое весит около восьми мегабайт, вместе — двести сорок мегабайт. Ещё он хочет добавить короткое видео о том, как готовят фирменную пиццу, — четыреста пятьдесят мегабайт.

Если сделать загрузку «в лоб», одним запросом со всеми файлами, случится вот что.

Несколько минут ничего не происходит. Кнопка нажата, на экране крутится спиннер, и непонятно, загрузилась уже половина или ничего. Менеджер нажимает «Сохранить» ещё раз.

Связь пропала на девяноста пяти процентах. Он зашёл в лифт — и всё начинается с нуля, хотя четыреста мегабайт уже ушли в сеть.

Часть фото не подходит. Сервер принимает фото до десяти мегабайт, а несколько снимков с новой камеры весят по двенадцать. Об этом менеджер узнаёт после того, как ждал пять минут.

Серверу тяжело. Сотни мегабайт идут через сервер приложения, который в это время должен быстро отвечать на запросы покупателей.

Загрузка файла — не обычный запрос. Она долгая, тяжёлая и часто идёт по плохой мобильной сети. Поэтому её проектируют отдельно: что видит человек, что делать при обрыве, через кого идут байты и сколько файлов отправлять одновременно.

=== раздел ===

Начнём с основных понятий.

Файл в браузере — объект, у которого есть имя, размер в байтах, тип и дата изменения. Сам файл браузер не читает целиком в память, пока вы этого не попросите. От файла можно отрезать кусок, не копируя весь файл.

Прогресс загрузки — сколько байт уже отправлено из скольких. Браузер сообщает его событиями прогресса у запросов, сделанных через икс-эм-эл-эйч-ти-ти-пи-реквэст. У фетч такого события для отправки на момент написания нет, поэтому полосу прогресса обычно делают на икс-эм-эл-эйч-ти-ти-пи-реквэст.

Отмена загрузки — прерывание запроса на клиенте: у икс-эм-эл-эйч-ти-ти-пи-реквэст для этого есть свой метод, а у фетч — эборт-контроллер.

Загрузка по частям — файл режется на куски, и каждый уходит отдельным запросом.

Возобновляемая загрузка — после обрыва клиент продолжает с того места, где сервер перестал получать данные, а не с начала. Это место называют смещением: сколько байт сервер уже сохранил.

Объектное хранилище — отдельный сервис для файлов, например Amazon эс-три или совместимые с ним. Файлы там лежат по ключу — строке вроде «меню, ресторан сорок два, пицца».

Подписанная ссылка — адрес в хранилище, в который сервер приложения заранее вписал разрешение: «по этому адресу можно один файл с таким ключом положить в течение пятнадцати минут». Клиент отправляет файл прямо туда, минуя сервер приложения.

=== раздел ===

Дальше — жизненный цикл одной загрузки. У каждого файла свой путь, и удобно описать его состояниями, как в уроке «Процесс как набор состояний».

Выбран — человек выбрал файл, ничего ещё не отправлено.

Отклонён — клиент проверил тип или размер и сразу сказал, что не так.

В очереди — файл ждёт своей очереди на отправку; зачем очередь, разберём дальше.

Отправляется — идёт передача, видна полоса с процентами.

Обрабатывается — все байты ушли, но сервер ещё проверяет файл, уменьшает фото, перекодирует видео.

И конечные состояния: готово, ошибка или отменено.

Главная ловушка здесь — между «отправляется» и «обрабатывается». Сто процентов на полосе — это не «готово». Событие прогресса говорит, сколько байт браузер отправил в сеть, а не сколько сервер принял и сохранил. Известный учебник по JavaScript прямо пишет, что это событие подходит только для индикатора, а не для решения «что уже загружено». Видео после отправки ещё несколько минут перекодируется, и показывать его в меню как опубликованное рано. Поэтому у файла есть отдельное состояние «обрабатывается», и «готово» наступает только после ответа сервера.

Каждое состояние видно в интерфейсе: у файла в списке своя полоса, своя кнопка «Отменить» или «Повторить» и свой текст ошибки. Одна общая полоса на тридцать файлов прячет главное — какой именно файл не загрузился.

=== раздел ===

Теперь — проверка и предпросмотр на клиенте.

Проверить файл до отправки — значит сэкономить человеку минуты ожидания. Обычно проверяют три вещи.

Тип. Особый атрибут в поле выбора файла сужает список в окне выбора, например только до картинок, а тип выбранного файла позволяет отклонить лишнее после выбора.

Размер. Его сравнивают с лимитом сервера.

И для картинок — размеры в пикселях, если меню требует, например, не меньше восьмисот точек по ширине.

Предпросмотр делают без загрузки на сервер: браузер даёт для файла временный адрес, который можно поставить в картинку на странице. Пока такой адрес существует, браузер не может освободить связанный с ним файл, поэтому, когда превью больше не нужно, адрес освобождают отдельным вызовом. Память съедают и сами показанные превью: браузер хранит каждую картинку раскодированной, по несколько байт на точку. Тридцать снимков с камеры в полном размере — заметная нагрузка на дешёвый телефон, поэтому превью показывают маленькими и по мере прокрутки.

Клиентская проверка — подсказка, а не защита. Браузер определяет тип файла по расширению имени и не читает содержимое: дайте программе имя картинки, и браузер сочтёт её картинкой. А запрос в обход интерфейса можно отправить вообще без всяких проверок. Поэтому сервер проверяет файл сам — по содержимому, размеру и доступу пользователя. Это тот же принцип, что в уроке «Формы и валидация»: клиент помогает человеку, сервер принимает окончательное решение.

=== раздел ===

Дальше — через свой сервер или напрямую в хранилище. Есть два пути, по которым байты могут попасть в хранилище.

Первый — через сервер приложения. Клиент отправляет файл на ваш API, сервер его принимает и сам кладёт в хранилище. Просто и всё под контролем: сервер видит файл целиком, может сразу его проверить. Но каждый мегабайт проходит через ваш сервер дважды — сначала внутрь, потом в хранилище. Сервер держит соединение всё время загрузки, а у серверов приложений обычно есть лимит на размер тела запроса.

Второй — напрямую по подписанной ссылке. Загрузка идёт в три шага.

Первый шаг: клиент просит у API разрешение — «хочу загрузить фото пиццы, восемь мегабайт, картинку, для блюда номер сорок два». Сервер проверяет доступ, сам выбирает ключ файла и возвращает подписанную ссылку со сроком действия.

Второй шаг: клиент отправляет файл по этой ссылке прямо в хранилище.

Третий шаг: клиент сообщает API, что файл по ключу такому-то загружен. Сервер проверяет, что объект действительно появился, смотрит его настоящий размер и тип и только тогда привязывает фото к блюду.

Сервер приложения при этом обрабатывает два коротких запроса вместо сотен мегабайт.

=== раздел ===

Цена у прямой загрузки тоже есть.

Ссылка работает как ключ от двери. Документация эс-три называет подписанные ссылки токенами на предъявителя: кто знает ссылку, тот и загружает, причём несколько раз, пока не истёк срок. Поэтому срок делают коротким — минуты, а не дни.

Размер на первом шаге — со слов клиента. Подписанная ссылка на запрос пут обычно не ограничивает размер файла, если длину не вписали в подпись: по ней можно отправить и восемь мегабайт, и пять гигабайт. Ограничить размер заранее позволяет другой вид подписи — форма для пост-запроса с политикой, в которой есть условие на размер, «от стольких-то до стольких-то байт». Файл больше лимита хранилище отклонит само. Иначе размер проверяют на третьем шаге и лишнее удаляют.

Сервер не видит файл до того, как тот попал в хранилище. Проверку содержимого он делает после загрузки, на третьем шаге или отдельной обработкой.

Брошенные файлы. Если клиент загрузил файл и закрыл вкладку до третьего шага, в хранилище лежит объект, на который никто не ссылается. Такие объекты удаляет правило очистки в хранилище.

И хранилище нужно настроить так, чтобы оно принимало запросы со страниц вашего сайта, — это корс. А тип файла в запросе должен совпадать с тем, что вписан в подпись, если сервер его туда вписал, иначе хранилище откажет.

=== раздел ===

Теперь — большие файлы: по частям и с возобновлением.

Видео в четыреста пятьдесят мегабайт на мобильной сети грузится несколько минут, и за это время связь почти наверняка мигнёт. Если загрузка идёт одним запросом, обрыв на четырёхсотом мегабайте означает начать заново. Решение — резать файл на части и уметь продолжить.

Как это устроено. Файл делится на части, например по восемь мегабайт: видео в четыреста пятьдесят мегабайт — это пятьдесят семь частей, пятьдесят шесть полных и одна неполная. Каждая часть уходит отдельным запросом. Если запрос упал, повторяют только эту часть, а не весь файл. Чтобы продолжить после обрыва, клиент спрашивает у сервера, что у того уже есть, и досылает остальное.

Решающий момент: о том, что уже загружено, знает только сервер. Клиент не может посчитать это сам по событиям прогресса: последний кусок мог уйти в сеть, но не дойти. Поэтому любое возобновление начинается с вопроса серверу.

=== раздел ===

Есть два распространённых способа.

Первый — протокол тас, открытый протокол возобновляемой загрузки поверх HTTP. Клиент создаёт загрузку пост-запросом и получает её адрес. Потом отправляет байты запросами патч с заголовком, где указано смещение — с какого байта начинается кусок. После обрыва клиент делает запрос хэд и получает в ответе смещение: столько байт сервер уже сохранил. Если клиент пришлёт кусок не с того места, сервер ответит кодом четыреста девять и ничего не испортит. Это тот же код, что при конфликте версий, но смысл здесь свой — «спроси смещение и продолжи с него». Поэтому клиент разбирает код четыреста девять в контексте запроса, а не сам по себе.

Второй — загрузка частями в эс-три. Клиент или сервер начинает загрузку и получает её номер. Части с номерами от одного до десяти тысяч можно отправлять в любом порядке и параллельно, каждая — не меньше пяти мегабайт, кроме последней. На каждую часть хранилище возвращает метку и-тэг; номер части и метку нужно запомнить. В конце отправляют запрос «собери файл» со списком всех номеров и меток. Эс-три советует такую загрузку для файлов от ста мегабайт. Часто каждую часть отправляют по своей подписанной ссылке.

=== раздел ===

Возобновление после перезагрузки страницы. Если человек обновил страницу, браузер забыл выбранный файл. Номер загрузки и список готовых частей нужно сохранить в хранилище браузера — локал-сторэдж или индексд-ди-би; о выборе хранилища говорили в уроке «Работа без сети и очередь действий». Когда человек снова выберет тот же файл, клиент узнает его по отпечатку — имени, размеру и дате изменения — и предложит продолжить. Сам файл тоже можно положить в индексд-ди-би, но это копия на сотни мегабайт на устройстве.

Незаконченные загрузки обходятся в деньги. Части в эс-три хранятся и оплачиваются, пока загрузку не завершат или не отменят. Поэтому кнопка «Отменить» отправляет серверу запрос на удаление — в тас это DELETE, в эс-три — отмена загрузки частями. А для брошенных загрузок в хранилище настраивают правило «удалять незавершённые через несколько дней».

У отмены в эс-три есть тонкость: части, которые ещё шли в момент отмены, могут успешно загрузиться и после неё. Поэтому сначала прерывают запросы частей, дожидаются, пока они завершатся, и только потом отменяют загрузку.

=== раздел ===

Дальше — сколько файлов отправлять одновременно.

Кажется, что тридцать фото быстрее всего отправить сразу все. Посчитаем. Тридцать фото по восемь мегабайт — двести сорок мегабайт. Пусть сеть отдаёт десять мегабит в секунду, это примерно одна целая двадцать пять сотых мегабайта в секунду. Вся пачка уйдёт за двести сорок, поделённые на одну целую двадцать пять сотых, — это около ста девяноста секунд, как ни крути: канал один.

Если отправлять все тридцать сразу, канал делится на тридцать частей. Каждое фото идёт со скоростью около четырёх сотых мегабайта в секунду, и все они заканчиваются почти одновременно — примерно через сто девяносто секунд. Три минуты менеджер не видит ни одного готового фото.

Если по три за раз, каждое фото идёт со скоростью около сорока двух сотых мегабайта в секунду и загружается примерно за девятнадцать секунд. Первые фото готовы через девятнадцать секунд, дальше новые появляются каждые несколько секунд, а вся пачка уходит за те же сто девяносто секунд.

Общее время одинаковое, а ощущение совсем разное. Кроме того, у очереди есть ещё плюсы: при обрыве под удар попадают три загрузки, а не тридцать; меньше памяти уходит на одновременные запросы; человек может переставить или отменить файлы, которые ещё ждут. Поэтому при выборе многих файлов делают очередь с ограничением параллельности: одновременно идут две-четыре загрузки, остальные ждут.

Браузер и сам не откроет по протоколу HTTP версии один точка один больше шести соединений к одному адресу, так что «все тридцать сразу» на деле превратятся в очередь из шести. Но это очередь, которую приложение не видит: в каком порядке пойдут файлы, что делать с отменой и что показывать у ждущих, решает не оно. Своя очередь отдаёт всё это вам.

=== раздел ===

Теперь — отмена и повтор.

Отмена. Кнопка «Отменить» прерывает запрос на клиенте. Но, как в уроке «Гонки запросов», отмена ожидания не отменяет то, что уже произошло на сервере: часть байт или частей может быть уже сохранена. Поэтому отменённую загрузку явно удаляют на сервере, а у файла в интерфейсе состояние «отменено», а не «ошибка».

Повтор. Временный сбой при отправке части повторяют с растущей задержкой и лимитом попыток — это правила из урока «Когда и как повторять». Повтор части безопасен: в эс-три часть с тем же номером просто перезапишет прежнюю, а в тас сервер примет только кусок с правильным смещением. А вот последний шаг — «привяжи фото к блюду» — это команда с эффектом, и повторять её нужно с ключом идемпотентности из урока «Повторы без двойных списаний», иначе к блюду привяжутся два одинаковых фото.

=== раздел ===

Теперь пример целиком: фото и видео в кабинете ресторана. Соберём всё вместе для менеджера с тридцатью фото и видео в четыреста пятьдесят мегабайт.

Выбор. Менеджер выбирает файлы. Клиент сразу показывает превью и отклоняет четыре фото по двенадцать мегабайт с понятным текстом: «Фото больше десяти мегабайт — уменьшите его или выберите другое». Видео проходит по типу и по лимиту в один гигабайт.

Очередь. Двадцать шесть фото и одно видео встают в очередь, одновременно идут три загрузки. У каждого файла своя полоса и кнопка «Отменить».

Фото — по подписанным ссылкам. Для каждого фото клиент получает у API ссылку на пятнадцать минут, отправляет файл одним запросом прямо в хранилище и сообщает API, что файл на месте. Сервер сверяет настоящий размер и тип объекта и удаляет его, если тот больше десяти мегабайт: проверка при выборе — только подсказка.

Видео — частями. Сервер начинает загрузку частями и выдаёт ссылки на части по восемь мегабайт. Клиент сохраняет номер загрузки и список готовых частей в индексд-ди-би.

Обрыв. В лифте связь пропадает на сороковой секунде видео. Части, которые не дошли, клиент повторяет с паузой, когда сеть возвращается. Всё, что уже сохранено, повторно не отправляется.

Перезагрузка. Телефон выгрузил вкладку из памяти. Менеджер открывает кабинет и видит: «Видео загружено на шестьдесят два процента. Выберите тот же файл, чтобы продолжить». Клиент узнаёт файл по отпечатку, спрашивает у сервера список готовых частей и досылает остальные.

Обработка. После последней части видео переходит в «обрабатывается»: сервер собирает его и перекодирует. В меню оно появится, когда сервер ответит «готово».

=== раздел ===

Дальше — какой способ выбрать.

Один запрос через свой сервер подходит для небольших файлов — аватара, документа на пару мегабайт — и когда сервер всё равно сразу обрабатывает файл. Цена — трафик идёт через сервер приложения, а обрыв означает загрузку с нуля.

Один запрос по подписанной ссылке подходит для фото и документов до десятков мегабайт, когда пользователей много. Цена — три шага вместо одного, настройка хранилища, брошенные файлы и проверка размера и содержимого после загрузки или подписанная форма с лимитом размера.

По частям с возобновлением — через тас или загрузку частями в эс-три — подходит для видео и архивов на сотни мегабайт по мобильной сети. Цена — сложнее клиент и сервер, нужно хранить номер загрузки и чистить незавершённые.

Ограничение параллельности и проверка на клиенте нужны в любом из вариантов, как только человек может выбрать много файлов.

=== раздел ===

Теперь о типичных ошибках.

Первая — считать сто процентов на полосе готовым файлом. Человек видит «загружено», а файл ещё обрабатывается или вовсе отклонён сервером.

Вторая — одна полоса на всю пачку. Непонятно, какой файл не загрузился и что повторить.

Третья — доверять клиентской проверке. Тип по расширению подделывается переименованием, а сервер, который не проверяет сам, примет что угодно.

Четвёртая — отправлять всё сразу. Ни один файл не готов до самого конца, а обрыв бьёт по всем загрузкам.

Пятая — возобновлять по своим подсчётам. Клиент решает, что отправил триста мегабайт, и продолжает с этого места, а сервер сохранил двести девяносто — файл получается битым.

Шестая — считать, что подписанная ссылка ограничивает размер. Ссылка на запрос пут примет файл любого размера; лимит держит подписанная форма с условием на размер или проверка на сервере после загрузки.

Седьмая — долгоживущие подписанные ссылки. Ссылка на неделю — это неделя, в течение которой кто угодно, кто её увидел, может положить файл в ваше хранилище.

Восьмая — забыть про брошенные загрузки. Незавершённые части и непривязанные файлы копятся в хранилище и обходятся в деньги.

=== раздел ===

Как об этом спрашивают на интервью.

Просят спроектировать загрузку фото в фотохостинг или загрузку больших файлов в облачное хранилище. Ждут прогресс по каждому файлу, очередь, проверку на клиенте и сервере, подписанные ссылки и возобновление.

Спрашивают: «Пользователь загружает видео на два гигабайта по мобильной сети, связь рвётся. Что вы сделаете?» Ждут загрузку по частям и то, что смещение берётся у сервера.

Спрашивают: «Почему не отправить файл через наш API?» Ждут сравнения трафика, нагрузки на сервер и цены прямой загрузки.

=== раздел ===

Коротко о главном.

Небольшой файл, который сервер сразу обрабатывает, отправляют одним запросом через свой сервер. Фото и документы до десятков мегабайт при многих пользователях — по подписанной ссылке. А видео и архивы на сотни мегабайт по мобильной сети — частями с возобновлением.

Между «отправляется» и «готово» у файла есть состояние «обрабатывается»: сто процентов на полосе — не «готово». Событие прогресса говорит, что отправил браузер, а «готово» наступает только после ответа сервера.

Прогресс отправки дают события икс-эм-эл-эйч-ти-ти-пи-реквэст, у фетч их на момент написания нет. У каждого файла своя полоса, кнопка и текст ошибки, а не одна общая полоса на пачку.

На клиенте проверяют тип и размер и показывают предпросмотр, чтобы сэкономить человеку ожидание. Это подсказка: тип файла берётся из расширения, и окончательно файл проверяет сервер по содержимому.

Загрузка по подписанной ссылке разгружает сервер приложения: клиент получает у API ссылку, отправляет файл прямо в хранилище и сообщает API, что файл на месте. Сервер проверяет настоящий размер и тип и только потом привязывает файл, а брошенные файлы удаляет правило очистки хранилища.

Подписанная ссылка — токен на предъявителя, поэтому срок у неё короткий. Запрос пут по ней обычно не ограничивает размер: лимит держит подписанная форма для пост-запроса с условием на размер или проверка после загрузки.

Большие файлы режут на части и возобновляют после обрыва — через тас или загрузку частями в эс-три. Что уже загружено, знает только сервер, поэтому возобновление начинается с вопроса серверу, а незавершённые загрузки удаляют: они обходятся в деньги.

При выборе многих файлов делают очередь с ограничением параллельности, две-четыре загрузки сразу: общее время то же, но первые файлы готовы быстро, а обрыв бьёт по немногим. Отменённую загрузку явно удаляют на сервере, потому что отмена на клиенте не отменяет сохранённого.
